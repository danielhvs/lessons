git rerere

Resolve a merge conflict once; git replays your fix every time the same conflict comes back.

1The problem

A merge conflict happens when two branches (lines of commits) changed the same lines differently: git stops and asks you to choose. Here main set color = red and feature set color = green in app.txt.

A long-lived branch that you rebase (replay its commits on top of another branch) onto main every week hits that same conflict every week, and you fix the same lines by hand each time.

rerere, short for reuse recorded resolution, records your fix the first time and replays it every later time.

2The smallest example: turn it on, conflict, fix once

rerere is off by default. One setting turns it on for every repo on the machine: git config --global stores it in ~/.gitconfig. Nothing is written to disk yet: the notebook folder .git/rr-cache/ appears the first time rerere records a conflict.

git config --global rerere.enabled true git config --get rerere.enabled true ls .git/rr-cache ls: cannot access '.git/rr-cache': No such file or directory

Now merge. The output has one extra line from rerere:

git merge feature Auto-merging app.txt CONFLICT (content): Merge conflict in app.txt Recorded preimage for 'app.txt' Automatic merge failed; fix conflicts and then commit the result.
<<<<<<< HEAD
color = red
=======
color = green
>>>>>>> feature

Those <<<<<<<, =======, >>>>>>> lines are the conflict markers. rerere strips the branch labels (HEAD, feature), puts the two sides in a fixed order, and hashes the result with SHA-1, a function that turns any text into a 40-character code. That hash is the conflict's fingerprint. The conflict itself is saved as the preimage: the "before" picture.

Resolve it by hand like always, here as color = teal, and commit. rerere saves your result next to the preimage as the postimage: the "after" picture.

git add app.txt git commit --no-edit Recorded resolution for 'app.txt'. [main 4c1962c] Merge branch 'feature' ls .git/rr-cache/* postimage preimage

3The same conflict again: replayed

Throw the merge away and merge again. Same conflict text, same hash, so git finds the folder and writes the postimage into the file.

git reset --hard HEAD~1 git merge feature Auto-merging app.txt CONFLICT (content): Merge conflict in app.txt Resolved 'app.txt' using previous resolution. Automatic merge failed; fix conflicts and then commit the result. cat app.txt color = teal git status --short UU app.txt

The file is already fixed but still marked UU, git's status code for "unmerged: both sides changed it". rerere leaves the last look to you: check the file, then git add and commit.

4Skip the git add: autoUpdate

Set rerere.autoUpdate and git also stages the replayed file (adds it to the index, as git add does). The message says Staged and the status goes from UU to M: only the commit is left.

git config --global rerere.autoUpdate true git merge feature Auto-merging app.txt CONFLICT (content): Merge conflict in app.txt Staged 'app.txt' using previous resolution. Automatic merge failed; fix conflicts and then commit the result. git status --short M app.txt

Trade-off: a replayed fix gets staged without you looking at it. Leave autoUpdate off if you want to review every replay.

5Sides flipped and rebase: still the same hash

In a conflict, ours is HEAD, the branch you stand on (top half), and theirs is the side coming in (bottom half). Stand on feature and merge main: the same clash, now with green on top. rerere sorts the two sides before hashing, so the fingerprint still matches.

git switch feature git merge main Auto-merging app.txt CONFLICT (content): Merge conflict in app.txt Resolved 'app.txt' using previous resolution. Automatic merge failed; fix conflicts and then commit the result.

A rebase replays the same conflict too, so it gets the same fix (autoUpdate off here; the rebase also prints its usual hint: lines, trimmed):

git rebase main Rebasing (1/1)Auto-merging app.txt CONFLICT (content): Merge conflict in app.txt error: could not apply e0899ed... feature Resolved 'app.txt' using previous resolution. Could not apply e0899ed... # feature

6A new example: a weekly rebase

config.yml conflicts the same way each time you rebase your branch, once a week for 5 weeks. Week 1 you resolve it by hand and rerere records it; weeks 2 to 5 replay that fix. Total: 1 fix by hand, 4 replays.

7Common mistakes

Recording a bad fix. rerere replays whatever you recorded, mistakes included. Fix: git rerere forget app.txt deletes the recorded fix for that file's conflict; merge again and resolve it properly.

git rerere forget app.txt Updated preimage for 'app.txt' Forgot resolution for 'app.txt' git merge --abort && git merge feature Auto-merging app.txt CONFLICT (content): Merge conflict in app.txt Recorded preimage for 'app.txt' Automatic merge failed; fix conflicts and then commit the result.

Expecting a teammate to get your fix. .git/rr-cache/ lives inside your .git folder: it is not committed or pushed, so each clone builds its own. Fix: each person turns rerere on and resolves once.

Committing a replay without looking. With autoUpdate on, the replayed file is already staged, so git commit takes it as is. Fix: run git diff --cached before committing, or leave autoUpdate off.

Assuming it is on. rerere is off by default, so nothing is recorded until you set rerere.enabled true.

Summary

  1. git config --global rerere.enabled true turns it on once.
  2. First conflict: rerere saves it as the preimage, under a hash of the conflict text.
  3. Your committed fix becomes the postimage; the same conflict later gets it replayed (still UU, or staged with autoUpdate).
  4. git rerere forget <file> drops a bad fix; git rerere gc prunes old records (unresolved after 15 days, resolved after 60, by default).
  5. rr-cache is local: not pushed, each clone builds its own.
